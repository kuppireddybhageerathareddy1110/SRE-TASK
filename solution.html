Take-home solution · sockets · concurrency · replication

A key-value store, replicated three ways, over plain TCP.

One proxy that clients talk to. Behind it, three interchangeable, entirely dumb in-memory stores. A write reaches every copy that's up; a read is answered by one of them — or by all of them, once Stage 5 turns the dial. No database, no consensus library, no framework: sockets, a dict, and a lock.

Where it ends up

One proxy, three dumb copies

The backends (kvserver.py) don't know a proxy exists, don't know about each other, and don't know how to replicate anything — they just keep a map and answer questions about it. Every decision about who's up, what to broadcast, and who to trust lives in proxy.py, which holds no data of its own. That split is what keeps each half small enough to hold in your head at once.

Same wire format, every hop

Protocol reference

Talking to a backend directly and talking to it through the proxy look identical to a client — same commands, same replies. Lines are plain text, one command per line, ending in \n, so a bare nc session drives either one.

Client sendsReplyIf missing
SET <key> <value>OK—
GET <key>VALUE <value>NOT_FOUND
DEL <key>OKNOT_FOUND
PINGPONG—
anything elseERR bad_commandconnection stays open

Three extra replies only the proxy ever sends, each meaning something different a client could branch on:

ReplyMeans
ERR backend_unavailableNothing is reachable to answer this at all.
ERR write_unavailableFewer than two copies are up — the write was refused by policy, not by failure.
ERR no_majorityStage 5 only: every copy that answered disagreed.

A store you can talk to over a socket

kvserver.py
The ask A TCP server holding an in-memory map, handling several clients at once, speaking the command table above — and coping gracefully with the one real surprise: TCP is a byte stream, so a single command can arrive in two separate reads.
  • Concurrent clients don't interfere — one thread per accepted connection, each with its own read buffer.
  • Commands split across reads are handled correctly — bytes accumulate in a per-connection buffer until a \n shows up; tested explicitly by sending "GE" then "T user:42\n" as two separate writes.
  • Bad input gets an error reply, not a crash — unrecognized commands return ERR bad_command and the connection stays open.
  • A plain nc session drives it correctly, byte for byte, per the table.
real output — nc 127.0.0.1 7101
SET user:42 alice OK GET user:42 VALUE alice SET user:42 alice smith # values may contain spaces OK GET nope NOT_FOUND FOO bar ERR bad_command # connection stays open PING PONG
The map is one dict behind one RLock — every read and write of it takes the lock for the duration of a single operation. Nothing fancier is needed at this scale, and reasoning about correctness stays trivial.

Put a proxy in the middle

proxy.py --backends host:port
The ask A second program that sits between client and server, invisibly — bytes flow both directions concurrently, and a dead backend produces an answer, not silence.
  • Fully transparent — talking to the proxy and talking to the backend directly give identical results.
  • Both directions run independently — each client connection is its own thread, and its calls to the backend block only that thread.
  • A dead backend fails fast — bounded by --op-timeout (default 1s), not a hang.
real output
== GET k through proxy (identical to talking to kv-1 directly) == SET k v OK GET k VALUE v == killing kv-1 == == GET k through proxy again == GET k ERR backend_unavailable
This stage's code path is Stage 3+'s general-purpose pass-through fallback, just with exactly one configured backend — one implementation covers both, controlled entirely by how many --backends you pass.

Broadcast every write to all three copies

proxy.py --backends h1,h2,h3
The ask Three copies behind the proxy. A write reaches every copy that's up and only succeeds if at least two are up to begin with; a read is spread across whichever copies are currently reachable.
  • Writes land on every up copy identically — verified by reading each backend's own port directly after a proxy write.
  • Copies are contacted concurrently, one thread each, joined together — a 3-way broadcast costs about as long as the slowest single copy, not the sum of all three (timed in tests).
  • Liveness is tracked two ways: a timer PINGing every copy, and any failed call marking that copy down immediately.
  • Reads rotate, not pinned to one copy — a shared counter, incremented modulo the current up-count.
  • Two down → writes refused, reads still work — and the two failure modes use distinct, tellable-apart error strings.
real output — killing copies as we go
SET cart:9 2xbook OK # all three stored it ... kill kv-2 ... SET cart:9 3xbook OK # two left, still fine ... kill kv-3 ... SET cart:9 4xbook ERR write_unavailable # only one copy left GET cart:9 VALUE 3xbook # reads still work
Deliberately not done here: acknowledging after two of three rather than waiting for every copy sent to. That's the quorum-write bonus — see below.

Bring a restarted copy back up to date

automatic, on whenever 2+ backends configured
The ask A copy that comes back after dying has an empty map. Before it answers reads again, it should learn the current contents from the longest-running survivor — using two new admin commands (INFO, DUMP) shaped however seems reasonable.
  • Deterministic "oldest" pick — highest INFO uptime wins, ties broken by name.
  • A recovering copy never serves reads early — read_ready stays false for the entire copy window, separate from up (which flips true immediately, so it doesn't fall further behind on writes while catching up).
  • Catch-up success is checked, not assumed — source and target key counts are compared and logged after the copy.
  • Live writes during the copy window survive — see the highlighted mechanism below.
The interesting bit: a recovering backend is added to the write broadcast set the instant it's seen alive — before its catch-up even starts. Any write that lands on it live is then protected by LOAD, a set-if-absent primitive: replaying the (older) snapshot from the source copy can only fill gaps, never overwrite a key the live write already touched. Full sequence in FLOW.md §7.
real output — kill kv-3, write more, restart it fresh
seed 5 keys, then kill kv-3 INFO INFO backends=3 up=2 read_ready=2 read_mode=roundrobin write key6 while kv-3 is still down SET key6 val6 OK restart kv-3 as a brand-new process (empty map, uptime resets to 0) -- proxy's own log during this window -- [proxy] backend kv-3 appears DOWN [proxy] backend kv-3 is back up [proxy] catching kv-3 up from kv-1 (uptime 2.37s) [proxy] kv-3 catch-up done: 6/6 snapshot keys applied, 6 keys now held (source had 6 at snapshot time) [proxy] kv-3 back in the read rotation ask kv-3 directly for keys it never saw live GET key1 VALUE val1 GET key6 VALUE val6 # written after kv-3 died — still present
Is "oldest" really best? It's a proxy for "most likely to have the fewest gaps," but not a perfect one — a longest-running copy could still have missed writes during a brief partition. Key count is a plausible alternative (measures completeness directly) but has its own blind spot: two honest copies can differ in key count purely from deletes. Uptime is what the brief asks for and is simpler to reason about, so it's the default.

When one copy disagrees, trust the majority

proxy.py --majority-read
The ask Ask all three copies for a value instead of one, trust whichever answer at least two agree on, and quietly correct the odd one out. A CORRUPT command, sent straight to one copy, exists purely to manufacture disagreement for testing.
  • Detects disagreement — every ready copy is queried concurrently, not just the first one to reply.
  • Returns the majority value, not the fastest reply.
  • Repairs the odd copy out with a direct SET/DEL.
  • The repair is logged, visibly, for a human to spot.
real output — after corrupting one copy
SET user:42 alice OK ... CORRUPT user:42 al?ce, sent straight to kv-3's own port ... GET user:42 # through the proxy, --majority-read VALUE alice # kv-1 and kv-2 outvote kv-3 ... a moment later, asking kv-3 directly ... GET user:42 VALUE alice # it got fixed [proxy] repaired kv-3 for key 'user:42' (had 'VALUE al?ce', majority said 'VALUE alice')
The named wrinkle: a copy that disagrees because it's corrupt and one that disagrees because it's merely behind look identical from the value alone — both get outvoted and overwritten today. A per-key version number is the real fix (a stale version says "behind, catch it up"; a current version with the wrong value says "corrupt, overwrite it") and is the top item in what's next, not yet built.
Also worth naming: majority-read triples read traffic (every GET now hits every ready copy). Worth leaving on permanently only if read capacity can absorb ~3× load in exchange for catching silent corruption on every read rather than only on a lucky round-robin draw.

Quorum writes

proxy.py --quorum-write

Acknowledges a write once a majority of the copies it was sent to confirm, rather than waiting for every one of them — the real-world version of Stage 3's rule.

What's traded away: the un-waited-for copy's write keeps running in the background; if it genuinely fails (not just slow), that copy is now silently missing a key while still marked healthy — no crash, no health-check signal. It's only fixed by Stage 5's read-repair, if enabled, or that copy's next restart. Durability breadth is traded for latency, and the safety net is the reader, not the writer.

Where the brief left it to me

Decisions & trade-offs

The brief's own advice: pick whatever seems reasonable where it doesn't say, write one line about why. These are those lines, slightly longer than one each.

Why two liveness signals (timer + opportunistic) instead of one?
A timer alone leaves a window where the proxy keeps trying a copy that just died mid-interval. Opportunistic-only never notices a copy that's silently hung with no current traffic to it. Both together cover each other's blind spot.
Why is ERR backend_unavailable reused for both Stage 2 and Stage 3+'s "nothing reachable" case, instead of a new name?
It's the same condition either way — the Stage 2 transcript in the brief already names it. A fourth invented error string (an earlier draft had ERR read_unavailable) would only fragment a client's error handling for no semantic gain.
Why threads, not asyncio?
Every workload here is small, blocking request/response pairs against a fixed, small set of backends — exactly the case the GIL doesn't penalize, and where asyncio's cooperative scheduling buys nothing over a thread per connection. The brief explicitly allows either.
Why one persistent connection per backend instead of reconnecting per call?
Reconnecting every call would conflate "is this backend reachable" with "can I complete a fresh handshake right now" — a slower, different question. A single long-lived link per backend, serialized by one lock, keeps the health-check's belief and the data path's belief the same thing.
What would the next day of work be spent on?
Per-key version numbers first — the one change that lets Stage 5 tell "behind" apart from "corrupt" instead of treating both the same. Then a checksum-based (not just key-count) catch-up verification, and a small chaos script exercising random kill/restart/corrupt against the live test cluster for confidence beyond the scripted failure points the current tests hit.

Testing

test_kvstore.py spins up real OS subprocesses and drives them over real sockets — the entire point of this exercise is what happens when a process actually disappears, which a mock can't do. 14 tests, all five stages plus the bonus, run with python3 test_kvstore.py.
